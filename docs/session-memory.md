# 会话记忆与上下文预算
## 两层机制
| 层 | 作用 | 代码 |
|---|---|---|
| 上下文预算（256K token） | 保证请求不会超出模型窗口：超了就从最早的轮次开始丢 | `services/chat/contextBudget.ts` |
| 会话记忆（markdown） | 补偿被丢弃的内容：压成要点存下来，每次请求放进 system prompt | `services/chat/memory.ts` |
只有预算没有记忆，超长对话就是"静默遗忘"；加上记忆才谈得上续聊。
## 预算
- `CONTEXT_INPUT_BUDGET = 256_000`（用户指定）
- 依据：`deepseek-flash` 上下文 1M，输出上限 384K，256K 留足余量
- 对照：官方 App 单会话累计约 14.8 万字符（≈9 万 token），256K 约等于它 3 倍
## 记忆怎么来
1. 每次发请求前按 256K 裁剪历史
2. 如果本次丢弃的轮次里，有**还没并入记忆**的部分累计 ≥ 20K token（`MEMORY_UPDATE_THRESHOLD`），
   后台异步发一次摘要请求（不阻塞本次对话）
3. 摘要输出**完整的新记忆正文**，覆盖保存到 `session.memory`，并把 `memoryCoveredRounds` 推进到本次丢弃轮次数
4. 下一次请求的 system prompt 带上这段记忆
## 为什么让用户能编辑
摘要可能漏掉或改动关键设定，角色扮演场景下这是硬伤。所以记忆是**可见、可改、可清空**的：
会话头部「记忆」按钮 → 面板里直接编辑 markdown（有记忆时按钮高亮）。
## 失败处理
摘要请求失败只记日志，本次对话按"没有新记忆"继续发送——记忆是增强项，不能挡住主流程。
## 成本
- 主请求：256K 输入 ≈ $0.04（非高峰缓存未命中）
- 记忆更新：只在累计丢弃 ≥20K token 时触发，输入是一次被丢弃的原文（最多 6 万字符）
## 验证
### 单测（`tests/session-memory.test.ts`，8 条）
记忆拼进 system、阈值判断（不够就不更新）、摘要输入截断（保留头尾）、token 估算。
### 端到端（`/.verify/context/memory-e2e.py`）
60 轮 × 4 万字符会话 + 伪造摘要响应，拦下全部真实请求：
| 断言 | 结果 |
|---|---|
| 摘要请求触发次数 | 1 |
| 第一次主请求带记忆 | 否（此时还没记忆） |
| 第二次主请求带记忆 | **是** |
| 记忆内容确实注入 | 是（"旧书店店主"出现在 system 里） |
| 记忆面板显示 | 与摘要返回内容一致 |
| 主请求 messages | 120 → 22（256K 预算下） |
## 已知取舍
- 被丢弃的轮次在聊天记录里**没有视觉标记**（按要求不显示"省略了 N 轮"）；用户只能通过「记忆」面板看到补偿结果
- 摘要质量取决于模型，可能遗漏细节；用户需要能改
- 记忆固定 8K token 上限，超了靠提示词要求压缩，没有硬截断
